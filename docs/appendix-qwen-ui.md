# 附录，用 Qwen 做 UI 编辑模型的后训练（SFT + RL）

这是一份独立附录，不属于博客正文。它回答一个具体问题，拿 *Training Foundation Models with a Single Algorithm*（arXiv 2610.40564）的算法，去做以 Qwen 为基座的专业 UI 编辑模型，应该怎么设计管线、数据、算法实现、调参和基准测试。源码在仓库 single-algorithm-toy 的 `examples/qwen_ui/`，仓库地址 https://github.com/weiping/single-algorithm-toy 。

先交代证据的边界。论文的实验只到 1.24 亿参数的合成推理任务，以及 0.76B 参数的数学与代码 RL。UI 编辑和 Qwen 都没有论文证据。示例代码在随机初始化的小型 Qwen2 结构上运行过，真实 Qwen 权重和 GPU 上没有运行过。下文凡是论文给出的设置都标明出处，凡是我的建议都标明是建议，需要你自己做对照。

## 一，总体思路

UI 编辑模型的输入是当前 UI 状态加一条编辑指令，输出是编辑后的 UI 状态。它有一个难得的条件，结果可以由程序判对错，比如结构化比对、约束检查或渲染差异。这正是论文算法的适用场景，因为论文的 RL 部分从二元奖励出发。

整体分两段。SFT 阶段用人工或合成的示范，教会模型输出格式和基本编辑操作。RL 阶段用验证器给出的 0/1 奖励，磨尖组合编辑这类示范里覆盖不足的能力。论文带来四点可以直接用的东西。

- 一个损失处理所有数据。SFT 示范和 RL 采样出的回答，都写成带逐 token 权重的序列，用同一个加权似然损失训练。
- RL 的权重只由本组通过率决定。一道题采样 N 条，答对 k 条，正确回答权重取 N/k（即 1/p̂），错误回答为 0，全错的题整体记零，不需要价值模型。
- 配比是一条随训练进度变化的曲线。分阶段训练是占比取 0 或 1、阶段边界跳变的特例。在 RL 阶段继续混入少量 SFT 示范，是论文里的一种做法，用来减少窄化与遗忘。
- 用最终模型在真实任务上的表现选检查点，不用阶段内的指标。

不适合的情形也要说清。如果你的 UI 编辑质量主要靠审美或模型打分，没有程序化的对错判定，奖励就不是二元的，论文的推导需要改造，这部分请读原文的连续奖励变体再决定。

## 二，管线

```
原始 UI 数据 ─ 清洗或合成 ─> sft.jsonl  rl.jsonl  eval_*.jsonl  retention.jsonl
                                  │
Qwen 基座 ── SFT（配比曲线 sft=1）──> 检查点 A
                                  │
              RL（配比曲线 rl≈1，混入少量 sft）──> 检查点 B，按间隔保存
                                  │
                   benchmark.py 评测并选出最终模型
```

对应到代码，`hf_unified.py` 负责 SFT 与 RL 两段，由配置文件里的曲线决定每一步的数据来源和学习率。`benchmark.py` 负责评测。`ui_task.py` 是内置的可验证任务，`data_jsonl.py` 是接入你自己数据的入口。

## 三，数据格式

数据放在一个目录里，每行一个 JSON。

| 文件 | 内容 | 用途 |
|---|---|---|
| `sft.jsonl` | `{"prompt": ..., "target": ...}` | SFT 示范，RL 期间也从这里取回放数据 |
| `rl.jsonl` | 同上，target 供验证器使用 | RL 提示 |
| `eval_<名字>.jsonl` | 同上 | 评测集，可以有多个，例如留出组合、已见组合 |
| `retention.jsonl` | 同上，可选 | 留出的示范，度量保留性 |

prompt 是模型看到的完整输入文本，包含 UI 状态和编辑指令。训练器会把评测集和 retention 的 prompt 从 sft 与 rl 里剔除，保证留出。仓库里的 `make_jsonl_demo.py` 可以把内置任务导出成这种目录，作为格式样例。

进入训练器之后，每个样本是 token 序列加逐 token 权重。

| 来源 | 提示部分权重 | 回答部分权重 | 回答 token 是否计入分母 |
|---|---|---|---|
| SFT 示范 | 0 | 1 | 是 |
| RL 回答，答对 | 0 | N/k | 是 |
| RL 回答，答错或全错的题 | 0 | 0 | 是，权重为零也计入 |
| 通用语料（预训练或中训） | 1 | 1 | 是 |

状态表示有几条建议，都不是论文的结论。让模型输出完整的新状态，比输出补丁更容易验证，代价是序列更长，状态很大时可以改成补丁，验证器改为应用补丁后再比较。状态要有规范化的顺序和格式，否则验证器会把等价输出判错。把组合编辑，也就是一条指令含多个操作，放进留出集，这样能测到组合泛化。

聊天模型的提示用分词器的聊天模板包装，回答以结束符收尾。`hf_unified.py` 提供 `--chat-template` 和 `--eos-token`，Qwen 聊天模型的结束符通常是 `<|im_end|>`，请用你的分词器核对。这两个选项没有在真实 Qwen 分词器上运行过。

## 四，验证器与奖励

奖励是二元的，逐项完全一致才得 1。论文的约定是，回答触到长度上限而没有结束符，奖励记 0。`data_jsonl.py` 内置三个验证器。`exact` 比较整段文本，`lines_equal` 逐行比较，`json_equal` 把输出和标准答案解析成 JSON 后比较结构，键顺序无关，解析失败记 0。

换成你的任务时，验证器是最需要认真做的部分。几条实践建议，同样不属于论文。要做规范化，让所有等价的输出判为同一个结果。要防止输出原样抄回输入就能得分，也就是提示里要有足够比例的必须改动才能判对的题。要让每道题的通过率不要长期为零，全错的题没有可模仿的对象，对梯度没有贡献，可以先用 SFT 把难度拉到有一定通过率，或者分难度逐步引入。

## 五，算法实现

四个部件都很短，下面是核心片段，完整代码在 `hf_unified.py` 和仓库根目录的 `unified.py`。

一，加权似然损失。分母是批内非提示 token 的总数，权重为零的回答 token 也在其中。

```python
logits = model(input_ids=ids, attention_mask=att).logits[:, :-1].float()
nll = -F.log_softmax(logits, -1).gather(-1, ids[:, 1:].unsqueeze(-1)).squeeze(-1)
denom = resp[:, 1:].sum().clamp(min=1.0)
loss = (nll * w[:, 1:]).sum() / denom
```

二，RL 权重。一道题的 N 条回答里答对 k 条，正确回答权重 N/k，其余为零。

```python
def rl_weights(correct, objective="maxrl"):
    n, k = len(correct), sum(correct)
    if k == 0:
        return [0.0] * n
    a = n / k if objective == "maxrl" else 1.0
    return [a if c else 0.0 for c in correct]
```

三，混入示范数据，按累计 token 取整。目标占比 f 很小时，每步不足一条示范，如果每步至少加一条，实测占比会偏高。

```python
class MixAccountant:
    def add(self, ratio, rl_tok, draw):      # ratio = f / (1 - f)
        self.want += ratio * rl_tok
        out = []
        while self.got < self.want:
            ex = draw(); out.append(ex); self.got += loss_tokens(ex)
        return out
```

四，生成与训练解耦。生成器可以是落后的权重副本，每隔 `--sync-every` 次更新同步一次，论文的异步系统取 4。RL 阶段的优化器从新的开始。

和论文做对照时要知道几处差异。论文把目标占比按事先估计的平均长度换算成条数，实测占比会随回答长度变化，本实现按累计的实际 token 记账，更贴近目标。论文真实数据实验采样用 top-k 50 与 top-p 0.95，并把被截掉的 token 排除在损失与计数之外，本实现采用论文受控实验的设置，温度 1、不截断，避开这个问题。论文的分阶段对照用了基线减法，统一训练的 MaxRL 权重不含基线。本实现是单进程模拟异步，没有分布式，分布式下分母要跨卡汇总，这一点论文没有讨论，需要你自己验证。

## 六，配比轨迹

配置文件有两种写法。第一种是每个来源一条曲线，分阶段与统一都用它。横坐标相同的两点表示跳变。

```json
"weight": {"sft": [[0, 1], [400, 1], [400, 0.15]],
           "rl":  [[0, 0], [400, 0], [400, 0.85]]},
"lr": [[0, 1e-3], [400, 1e-3], [400, 1e-4]]
```

第二种是论文式的 `mix_progress`，直接给出示范 token 占 RL 回答与示范总 token 的比例，自变量是训练进度 u，取值 0 到 1。论文比较了四种平均占比都是 0.5% 的调度，仓库里各有一份配置。

| 调度 | 公式（a = 0.005） | 配置文件 |
|---|---|---|
| 恒定 | a | `rl_sched_0p5_const.json` |
| 全程退火 | 2a(1−u) | `rl_sched_full_anneal.json` |
| 线性增长 | 2au | `rl_sched_growth.json` |
| 半程退火 | 4a·max(1−2u, 0) | `rl_sched_half_anneal.json` |

论文的结论是时机本身是一个独立的变量。半程退火的最终代码准确率更高，但留出损失的改善保留得更少，所以哪种更好取决于你更看重哪项指标。比例、成分和时机三者互相牵连，不要只调一个。针对 UI 编辑，还可以考虑在 SFT 阶段混入通用指令数据来保护通用能力，这是我的建议，论文没有做这个实验。

## 七，调参

下表左侧是论文的设置，右侧是我给 Qwen UI 编辑的起点建议。论文明确说没有研究最优学习率和批大小，所以学习率需要你自己扫。

| 项目 | 论文设置 | 起点建议 |
|---|---|---|
| RL 优化器 | AdamW，每次 RL 从新的优化器开始，恒定学习率，无预热 | 同论文 |
| RL 学习率 | 受控实验 1e-5（1.24 亿参数），真实数据实验 1e-6（0.76B） | 从 1e-6 起，按倍数扫 |
| 权重衰减与梯度裁剪 | 0.01 与 0（两组实验），裁剪均为 1 | 权重衰减 0，裁剪 1 |
| 每次更新 | 32 题 × 16 条（受控）；512 条回答（真实数据） | 先用较小规模，题数与每题条数 N 都要扫 |
| 采样 | 温度 1，top-p 1；真实数据 top-k 50 与 top-p 0.95 | 温度 1，不截断 |
| 最大回答长度 | 1280 与 1024 个 token | 按你的 UI 状态长度定，留出余量 |
| KL 惩罚与熵奖励 | 都不用 | 同论文，实验里 KL 会同时拉低主任务 |
| RL 期间混入比例 | 0.5% 到 5%（真实数据） | 先试 0.5%、2%、5%，并设 0% 对照 |
| 调度 | 恒定、全程退火、线性增长、半程退火 | 先恒定，再比较半程退火 |
| 生成器同步周期 | 每 4 次更新 | 4 |
| 中训或 SFT 阶段 | 扫 1、2、4 个 epoch，学习率 2e-4 与 5e-5，按最终 RL 准确率选 | 同样按最终 RL 后的表现选，不按 SFT 阶段指标选 |

调参顺序建议如下。先固定一个能跑通的 SFT 检查点，再按这个次序扫，RL 学习率、每次更新的题数与每题条数、混入比例、调度、同步周期。每一步都用同一个初始化、同一条数据流、同样的算力和多个种子，选择标准是最终模型在评测集上的表现。算力用论文的估计式记账，C = 6N(T_pre + T_mid) + 8N·T_rollout + 6N·T_mix，其中 8N 是生成的 2N 加一次训练的 6N，提示与回答的 token 都计入。`hf_unified.py` 在每次评测时打印累计算力。

## 八，基准测试

指标与论文一致。每题独立采样 n 条，温度 1、不截断。准确率是 pass@1，覆盖率是 pass@k，用无偏估计从 n 条里算出，论文取 n=64、k=16。保留性用留出示范上每个回答 token 的负对数似然，对应论文的留出语料损失。通用能力再用一批外部通用基准的平均分来度量，论文用了五个通用基准，包括 SciQ 和 MMLU，你要换成适合 Qwen 的那一批。

评测集至少分三类。留出组合是 RL 的目标，已见组合和单操作用来观察没有被 RL 直接训练的能力有没有退化，retention 用来度量对 SFT 分布的保留。题目数太少时置信区间会很宽，`benchmark.py` 给出按题重采样的 95% 区间，题数不足时不要下结论。

```bash
python benchmark.py --model <Qwen 路径> --device cuda --dtype bfloat16 \
    --data-dir my_data --verifier json_equal --chat-template --eos-token "<|im_end|>" \
    --init rl_step500.pt --eval-samples 64 --eval-k 16 --out bench.json
```

下面是在随机初始化的小型 Qwen2 结构的 SFT 检查点上跑 `benchmark.py` 的输出，每题 32 条，pass@16 为无偏估计，每个评测集 48 题。它只用来展示工具链和报告格式，不说明任何方法的效果。

| 评测集 | 准确率 pass@1 | 覆盖率 pass@16 |
|---|---|---|
| 单操作 | 0.387 (0.296, 0.479) | 0.916 (0.859, 0.962) |
| 已见组合 | 0.242 (0.165, 0.324) | 0.729 (0.623, 0.832) |
| 留出组合 | 0.197 (0.118, 0.286) | 0.486 (0.359, 0.615) |

留出示范损失为 0.036，共 64 条。

真正的对比应当把候选配置各自的这张表并排放，同时给出算力。判断一个混入配置是否值得，要看三件事，留出组合有没有提升，已见组合与保留性有没有掉，覆盖率有没有被牺牲。

## 九，运行与自检

```bash
python test_ui.py                                   # 八项自检，几十秒
python hf_unified.py --tiny --config configs/sft_only.json --save sft.pt
python hf_unified.py --tiny --config configs/rl_only.json  --init sft.pt     # 0% 对照
python hf_unified.py --tiny --config configs/rl_mixed.json --init sft.pt     # 混入 15% 示范
python benchmark.py --tiny --init sft.pt --eval-samples 32 --eval-k 16
```

`test_ui.py` 的八项自检全部通过，覆盖验证器、数据隔离、损失与手算一致、无偏 pass@k、小比例下的混入记账、四种调度的平均占比、训练循环的实测配比，以及 JSONL 数据路径。仓库根目录另有 `check.py` 与 `verify.py`，验证算法本身，记录见 `docs/verification.md`。

## 十，没有验证的内容

示例没有在真实 Qwen 权重和 GPU 上运行过，聊天模板与结束符的处理是按通用接口写的，需要你用真实分词器核对。没有 LoRA，也没有分布式与独立的推理引擎，真实规模下生成应交给推理引擎，训练与生成各占一部分显卡。小模型上的运行记录只说明流程可用，`examples/qwen_ui/README.md` 里的对照数字评测只有 48 题和两个种子，不能外推。混入示范是否改善你的 UI 编辑模型，需要按上面的顺序做对照才能知道。
