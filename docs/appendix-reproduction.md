# 附录，复现论文：这份代码做到了哪一步

论文是《用单一算法训练基础模型》（*Training Foundation Models with a Single Algorithm*，arXiv 2610.40564），前身是《最大似然强化学习》（*Maximum Likelihood Reinforcement Learning*，arXiv 2602.02710）。源码在仓库 https://github.com/weiping/single-algorithm-toy 。

这份附录回答一个具体问题：**用这份代码，能复现论文到哪一步。** 结论先行：本仓库把论文的机制完整实现并逐条验证到了「实现与约定一致」这一步；论文的实验数值一步都没有复现，因为模型规模、数据、任务、评测口径全都换了。这不是缺陷，是刻意的取舍，下面逐条说明。

「复现」这个词有三个层次，混在一起谈会得出错误结论：

| 层次 | 问的问题 | 本仓库的状态 |
|---|---|---|
| 机制复现 | 论文的算法是否被正确实现 | 完成，且有精确数值验证 |
| 实现一致性 | 真实训练跑起来时是否按算法的约定行事 | 完成，有逐步运行记录核对 |
| 实验数值复现 | 论文图 4 到图 9 的曲线能否重现 | 未做，也不打算在这个规模上做 |

## 二、代码与论文的对应关系

论文第 4 节「Practical Implementation」的五件事，在仓库里各对应一个函数。`check.py` 的七项自检就是围绕这张表写的。

| 论文位置 | 论文的机制 | 仓库实现 | 自检项 |
|---|---|---|---|
| 4.1 数据格式 | 样本是 token 序列加逐 token 权重，提示部分权重为 0 | `unified.py` 的 `Example` / `lm_example` / `sft_example` / `rl_example` | 权重 |
| 4.1 式 (2) | 加权似然损失，分母是批内非提示 token 总数 | `unified.py` 的 `weighted_loss` | 损失分母 |
| 3.1 | ∇log p 等于在成功条件分布上的似然梯度 | `check.py` 的 `test_likelihood_identity`，用 6 个结果的类别分布精确验证 | 恒等式 |
| 4.2 | 有限 N 时，权重取通过率的倒数 N/k；全错的题整体记零 | `unified.py` 的 `rl_weights` | 权重 |
| 4.2 | 有限 N 的估计量期望等于 [1−(1−p)^N]·∇log p | `check.py` 的 `test_finite_n_expectation`，枚举全部 6^N 个结果 | 有限 N |
| 4.3 | 混合采样速率正比于 f_s / T_s，T_s 是该来源的平均损失 token 数 | `unified.py` 的 `MixtureSampler`，`pipeline.py` 的 `draw_mixed_batch` | 混合采样、配比曲线 |
| 4.3 | 生成与训练解耦，生成器用落后权重，每 k 次更新同步一次 | `unified.py` 的 `rl_phase`，`pipeline.py` 的 `run` 与 `--sync-every` | 策略滞后 |
| 附录 C.3 | 权重为零的全错回答，其 token 仍然计入损失分母 | `unified.py` 的 `weighted_loss` 里 `denom = resp[:, 1:].sum()` | 损失分母 |
| 4.1 | 配比是随训练进度变化的曲线，分阶段是占比取 0 或 1 的特例 | `pipeline.py` 的 `Curve` / `Schedule`，`configs/staged.json`、`configs/unified.json` | 配比曲线 |

两个论文里容易漏掉的细节，仓库都实现了并且单独验证：

- **全错回答计入分母**（论文附录 C.3）。全错回答权重为零，对梯度没有贡献，但它的 token 仍进分母。否则整组题的分母变小，剩下样本的更新会被悄悄放大。`check.py` 用一个恒等输出的假模型精确验证这一点。
- **提示掩码口径**（论文附录 C.2）。统一训练在预训练后段混入的中训序列对全部 token 算损失，包括提示；分阶段中训屏蔽提示。仓库在 `train.py` 里照此实现，两组并不只差在配比上。

仓库自己加的一条，不在论文里：**累计取整的混入记账**。论文的混合比例是连续的，但程序里一条条样本地补，小比例时每步至少补一条会让实测占比偏高。`pipeline.py` 改成按累计 token 只补欠账（`cum_want` / `cum_got`），`check.py` 与 `verify.py` 都覆盖了这个口径。

## 三、本地已经验证到什么程度

记录由仓库代码实际运行产生，环境为单核 CPU、PyTorch 2.15.0，完整输出见 `docs/verification.md` 与 `docs/four_stages_runs.md`。

### 3.1 公式级自检，`python check.py`

七项，几秒跑完，全部通过：

```
ok  权重：MaxRL 每题权重和为 N，全错记零，REINFORCE 权重为 1
ok  恒等式：∇log p = E_{成功条件分布}[∇log π]
ok  有限 N=3：期望梯度 = [1-(1-p)^N]·∇log p，p=0.392
ok  混合采样：目标 token 占比 0.7/0.3，实测 0.700/0.300，条数比 11.7:1

ok  数据：预训练语句 2605 条，留出 261 条且与训练集不相交；RL 提示流与评测题去重；留出组合不进中训
ok  配比曲线：跳变与线性段正确；分阶段每步只有一个来源；混合步 token 占比 0.3，实测 0.298
```

## 四、复现不了论文数值的地方，差在哪里

| 维度 | 论文 | 本仓库 | 差在哪 |
|---|---|---|---|
| 模型 | 124M（12 层、隐藏维 768、12 头）；0.76B | `TinyGPT` 806,656 参数（4 层、隐藏维 128、4 头） | 三个数量级 |
| 预训练语料 | 20B token，75% ClimbMix + 25% Dolmino | 2605 条程序生成的中缀算式 | 语料是生成出来的，词表 40 |
| 中训语料 | 510M token，逻辑谜题的 oracle 解答 | 同一生成器的示范数据 | 规模与难度都不同 |
| 任务 | 逻辑谜题 / 数学 / 代码 | 组合算术 | 验证器与奖励函数不同 |
| 评测 | pass@1、pass@16、pass@32；五个通用 benchmark | pass@1、pass@8；留出语句损失 | 口径不同，不能横向比 |
| 种子 | RL 取两个种子的平均 | 三个种子（toy）/ 一个种子（verify） | 统计效力弱 |
| RL 更新次数 | Base 6000 次，Extended 12000 次，持续学习 4000 次 | 62 次（verify）、150 次（train.py）、100 次（four_stages.py） | 差两个数量级 |
| 异步生成 | 8 个生成器 + 缓冲区，生成策略落后 12 到 44 次更新 | 单进程里用落后的权重副本 | 只验证逻辑，吞吐与陈旧度分布没有验证 |
| 分阶段基线的奖励权重 | 分阶段 MaxRL 用 (r − p̂)/p̂，统一训练用 r/p̂ | 两者都用 r/p̂ | **仓库的 `staged` 臂不能与论文的分阶段基线直接比**，见下 |
| KL 正则对照 | 附录 E 单独一节 | 没有 | 没有 |
| 四种调度 | 恒定 / 全程退火 / 线性增长 / 半程退火 | 曲线格式能表达 | 没跑 |

### 4.1 一个必须点名的差异：分阶段基线的奖励权重

论文附录 D.6 写明：统一训练按 r/p̂ 加权，分阶段 MaxRL 按 (r − p̂)/p̂ 加权，两者只差一个与提示相关的基线，on-policy 期望梯度相同，但有限样本下的更新不同，而且这个恒等式不适用于旧策略生成的数据。论文做零混合对照时，也特别说明分阶段基线是另一套同步实现，两者之间的差距里混着实现差异。

本仓库的 `unified.py` 只有 r/p̂ 一种权重，`train.py` 的 `staged` 臂用的也是它。所以：

- 仓库的 `staged` 与 `unified` 对比，是**同一套权重下配比轨迹的对比**，不是论文里统一训练对分阶段基线的对比；
- 论文图 5、图 7 里统一训练与分阶段基线之间的差距，不能用仓库的数字去解释，也不能用仓库的数字去反驳；
- 想做论文那种对比，`train.py` 需要补一个带基线减法的权重分支，这是本仓库明确没做的事。

### 4.2 即使在同一设定下，本仓库的对照也有解释上的限制

`train.py` 与 `four_stages.py` 的两份方案总步数相同，但统一方案在整个后半程持续看到中训与 SFT 数据，累计曝光量、学习率的安排都与分阶段不同。所以它们回答的是「同样的步数下，按曲线混合还是按阶梯切换」，推不出「相同数据量下统一更好」。四个指标上统一全面更好，也不能当成论文结论的确认——玩具规模、三个种子、只够看方向。

论文在受控实验里的结论其实也不是「统一全面更好」：在这个小规模设定里，中等算力预算下分阶段训练的准确率更省算力，统一训练在最大和最小预算上准确率更高。仓库看不到这种交叉。

## 五、要在自己的环境里复现论文，需要换什么

按层拆，每层的替换点都在仓库里有对应的位置。

**数据层。** `task.py` 整体替换。需要三样东西：预训练语料（ClimbMix + Dolmino 比例，或等价的网页文本）、中训语料（论文的逻辑谜题可换成任意带 oracle 解答的推理数据）、RL 题目与验证器（数学题用 veRL 的奖励函数，代码题用单元测试）。仓库现有的验证器接口只有 `task.is_correct(gen_ids, target)` 一个函数，替换成真正的验证器即可，其余逻辑不用动。

**模型层。** `model.py` 的 `TinyGPT` 换成真实模型。`examples/qwen_ui/hf_unified.py` 已经有一份：`HFTok` 处理分词与对话模板，`weighted_loss(model, examples, pad_id)` 是同一套加权似然损失，`MixAccountant` 是累计取整的混合记账，`evaluate(model, tok, sets, n, k, max_new, verify)` 是 pass@k 的评测。直接搬过去即可。

**训练层。** `pipeline.py` 的 `Curve` 与 `Schedule` 不用改，它们读的就是配比曲线。注意两点：

- 曲线取值会被归一化（`Schedule.fractions` 把各来源的原始值除以总和），所以配置里写的值应当本身就加起来等于 1，否则含义是相对权重；
- 同一个时刻只允许一个 RL 来源，`run` 里有断言。论文的对照实验大多符合这一点。

一份按论文 5.1 口径写的配置草案，注意形状而不是数字：

```json
{
  "total_steps": 26000,
  "sources": {
    "web":  {"kind": "lm",  "weight": [[0, 1], [8000, 1], [8000, 0.5], [20000, 0.5], [20000, 0]]},
    "mid":  {"kind": "sft", "weight": [[0, 0], [8000, 0], [8000, 0.5], [20000, 0.5], [20000, 0.15], [26000, 0.15], [26000, 0]]},
    "rl_A": {"kind": "rl",  "prompts": "A", "weight": [[0, 0], [20000, 0], [20000, 0.85], [26000, 0.85], [26000, 0]]}
  },
  "lr": [[0, 1e-3], [20000, 1e-3], [20000, 5e-5]],
  "eval_at": [8000, 20000, 26000],
  "eval_names": ["预训练后", "RL 前", "RL 后"]
}
```

横坐标相同的两个点表示跳变，所以这份配置是：前 8000 步只训预训练语料，接下来的 12000 步按 50:50 混入中训数据（论文里「预训练后段混入中训」的做法），最后 6000 步以 85:15 的比例跑 RL 与示范数据。三段的取值各自加起来等于 1，因此归一化这一步是空操作。

论文 5.2 的四种调度对应四条曲线，形态分别是恒定、线性降到零、线性从零升起、线性降到一半为零。下面只列出 `mid` 这一条来源，其余来源照旧：

```json
{"mid": {"kind": "sft", "weight": [[0, 0.005], [10000, 0.005]]}}
{"mid": {"kind": "sft", "weight": [[0, 0.01],  [10000, 0.0]]}}
{"mid": {"kind": "sft", "weight": [[0, 0.0],   [10000, 0.01]]}}
{"mid": {"kind": "sft", "weight": [[0, 0.02],  [5000, 0.0]]}}
```

四条曲线在整个区间上的平均值都是 0.5%，与论文「平均配置占比 0.5%」的口径一致；前三条的跨度是 10000 步，最后一条在第 5000 步就归零，区间之外保持为零。

**评测层。** `unified.pass_at_k` 给出 pass@1 与 pass@k，但论文用的 k 是 16（受控实验与持续学习）和 32（真实语料），改 `eval_k` 即可。留出语料损失换成论文口径：`heldout_loss` 现在算的是每 token 的负对数似然，论文报的是 nats/token 的变化量（如 +0.074、+0.047），需要相对基座模型做差。五个通用 benchmark 的平均分仓库没有，需要接外部评测。

**算力记账。** `unified.Meter` 是粗略口径（训练 6·P·token，生成 2·P·token），论文图 5 的横轴是累计算力，要对齐得换成自己的计数器，并且明确训练与生成是否都计入。

## 六、今天就能跑的五条命令

按代价从低到高排。前三条在任何有 PyTorch 的机器上都是分钟级。

```bash
pip install torch==2.15.0

python check.py                              # 七项公式级自检，几秒

python train.py --seeds 0 1 2                # 三种练法并排对照，写出 results.json
```

`train.py` 的三个臂对应论文的三种设定：`staged` 是分阶段流程，`unified` 是统一流程，`unified_rl0` 是论文附录 D.6 的零混合对照——只在预训练后段混入，RL 期间不混，用来把「混合的作用」与「RL 本身的作用」分开。三者共享同一个随机初始化与同一份数据流。

跑完这一套能得出的结论，按可信度排序：

1. **机制实现无误。** 恒等式、有限 N 的期望、权重和、混合占比、损失分母、策略滞后，这些是被精确验证的。
2. **真实训练按约定行事。** 每一步的来源、占比、权重、滞后都对得上。
3. **玩具规模下统一配比更划算。** 四个指标上统一全面更好。方向与论文一致，但这是 80 万参数、三个种子、几千条生成数据的结果，不能外推。
4. **不能推出论文的结论。** 论文的保留性、算力最优、持续学习收益、调度偏好，本仓库没有对应的实验。

## 七、读代码的顺序

想弄懂这份代码在做什么，按这个顺序读，一小时够了：

1. `docs/appendix-four-stages.md`——五个公式与四个阶段的最小实现，配合 `four_stages.py` 看，一份代码一个文件，没有依赖。
2. `unified.py`——算法本体。四个数据构造函数、`weighted_loss`、`rl_weights`、`MixtureSampler`、`rl_phase`，各二十行上下。
3. `pipeline.py`——把配比曲线接进同一个循环。`Curve` 与 `Schedule` 是读懂配比的入口，`run` 是全部逻辑所在。
4. `train.py`——三种练法并排，实验结构看这里。
5. `task.py`——任务与数据，注意留出集与评测集的去重逻辑。
6. `docs/verification.md`——上面每一段代码对应的运行记录。

想接到真实模型上，直接看 `examples/qwen_ui/hf_unified.py`，它把 `unified.py` 的四个部分逐一换成了 Hugging Face 版本，接口是一一对应的。
