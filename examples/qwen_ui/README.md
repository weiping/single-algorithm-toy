# examples/qwen_ui：在 Qwen 上做 UI 编辑模型的 SFT + RL（示例）

这个示例把仓库的统一训练算法接到 Hugging Face 因果语言模型上。它回答两个问题，论文的算法对 UI 编辑模型的后训练有没有帮助，以及怎么落地。

## 先说结论与边界

**可能有帮助的地方。** UI 编辑有一个很好的条件，输出可以被程序验证，比如结构化的 UI 状态与标准答案逐项比对、约束检查、渲染后的像素差。这正是论文算法的适用场景。

- RL 阶段继续混入 SFT 示范数据，可以降低 RL 把模型越练越窄、忘掉指令遵循与输出格式的风险。论文在数学 RL 上观察到混入 0.5% 到 5% 的前序数据几乎不影响主任务，却明显改善留出语料损失。
- MaxRL 的权重（正确回答 N/k，全错记零）可以直接套在你现有的验证器上，不需要价值模型，对难题更友好。
- 配比写成配置里的曲线，便于做对照实验，比如半程退火、早期混入与后期混入。

**证据的边界。** 论文的实验只到 1.24 亿参数的合成任务和 0.76B 参数的数学与代码 RL。没有 UI 编辑的证据，没有 Qwen 的证据，更大模型上是否成立也没有证据。所以应当把它当作一组要做 A/B 的假设，不能当作已知收益。

**这个示例做了什么、没做什么。** 沙箱没有网络访问 Qwen 权重，也没有 GPU。所以示例在随机初始化的小型 Qwen2 结构（约 79 万参数、字符级分词）上验证整条流程可以运行，并附上这个规模下的运行记录。它证明代码路径正确，不证明在真实 Qwen 上有效。换成真实 Qwen 需要你自己在 GPU 上运行，下面给出方法。

## 跑测记录

下面的记录由本目录代码在沙箱（单核 CPU，PyTorch 2.15.0，transformers 5.22.1）上实际运行得到，原始 JSON 和日志在 `runs/`。模型是随机初始化的小型 Qwen2 结构（793,984 参数），字符级分词，不是真实 Qwen，所以只能说明流程跑得通，以及这个规模下观察到了什么，不能外推到真实 Qwen。

**SFT。** 1500 步，只用单操作和已见组合的示范。评测 32 题、每题 4 次，单操作 pass@1 为 0.430，已见组合 0.172，留出组合 0.102。

**RL，从同一个 SFT 检查点出发。** 60 次更新，每次 16 题 × 8 条回答，MaxRL 权重，评测 48 题、每题 8 次。对照组 `rl_only` 不混示范，实验组 `rl_mixed` 按损失 token 占比混入 15% 的 SFT 示范。两个种子，数字为 RL 前到 RL 后的变化，括号内是两个种子各自的变化。

| 评测集 | 指标 | 不混示范 | 混入 15% 示范 |
|---|---|---|---|
| 留出组合（RL 训练的目标） | pass@1 | 0.212 → 0.306（+0.076，+0.112） | 0.212 → 0.301（+0.076，+0.102） |
| 留出组合 | pass@8 | 0.469 → 0.604（+0.125，+0.146） | 0.469 → 0.552（+0.083，+0.083） |
| 已见组合（没有被 RL 训练） | pass@1 | 0.266 → 0.199（−0.070，−0.062） | 0.266 → 0.245（−0.036，−0.005） |
| 已见组合 | pass@8 | 0.646 → 0.500（−0.167，−0.125） | 0.646 → 0.562（−0.104，−0.062） |
| 单操作 | pass@1 | 0.375 → 0.350 | 0.375 → 0.348 |

**怎么读这些数字。** RL 把留出组合的 pass@1 从 0.21 提到 0.30 左右，两组几乎一样。没有被 RL 训练的已见组合，在不混示范时下降约 0.07，混入示范后只下降 0.005 到 0.036，pass@8 的下降也更小，两个种子方向一致。单操作没有看出差别。

**这些数字的可信度很有限。** 评测只有 48 题，只有两个种子，两个种子共用同一个 SFT 检查点，种子之间差异是 RL 的随机性，没有覆盖 SFT 的随机性。已见组合的差距在噪声边缘，不能当作结论。混入 15% 也是为了在小模型上看出效应，比论文测的 0.5% 到 5% 大得多。真正的判断要在你的模型和你的验证器上做同样的对照。

下面的对照运行由混入记账修改之前的版本产生（当时每步至少补一条示范，15% 的目标占比下偏差很小，0.5% 这样的小比例下才明显）。修改后的代码用 `test_ui.py` 验证了小比例下的累计占比，这一组运行记录没有重跑。

## 文件

- `ui_task.py`：可验证的 UI 编辑任务。状态是若干行 UI 元素，指令是一到两个原子操作，奖励是逐行完全一致的 0/1。两种操作的先后组合只有一部分出现在 SFT 里，其余留给 RL 与评测，用来测组合泛化。
- `hf_unified.py`：训练器。样本是 (z, w)，一个加权似然损失同时处理 SFT 与 RL，配比由 `configs/*.json` 的曲线给出，生成器可以是落后的权重副本。
- `configs/`：`sft_only`、`rl_only`、`rl_mixed` 三份配置。
- `benchmark.py`：基准测试，无偏 pass@k、按题重采样的置信区间、留出示范损失。`metrics.py` 是指标，`data_jsonl.py` 是 JSONL 数据与验证器，`make_jsonl_demo.py` 导出格式样例。
- `test_ui.py`：八项自检，验证验证器、数据隔离、损失与手算一致、无偏 pass@k、小比例混入记账、四种混入调度、训练循环的实测配比和 JSONL 数据路径。
- 完整说明见 `../../docs/appendix-qwen-ui.md`。

## 运行（随机初始化的小模型，无需下载）

```bash
python test_ui.py
python hf_unified.py --tiny --config configs/sft_only.json --save sft.pt
python hf_unified.py --tiny --config configs/rl_only.json  --init sft.pt --seed 0   # RL 不混示范，对照组
python hf_unified.py --tiny --config configs/rl_mixed.json --init sft.pt --seed 0   # RL 期间混入 15% 示范
```

## 换成真实 Qwen

```bash
python hf_unified.py --model <你选定的 Qwen 模型名或本地路径> --device cuda --dtype bfloat16 \
    --config configs/rl_mixed.json --rl-prompts 64 --rl-n 8 --max-new 512 --sync-every 1
```

要改的地方有四处。

1. **任务与验证器。** 把 `ui_task.py` 换成你自己的 UI 状态表示和 `reward`。奖励保持二元最方便，论文的推导从二元奖励出发。如果你的判定是连续分数（比如渲染相似度），可以先用阈值转成二元，或参考论文对连续奖励变体的处理，这部分请读原文再决定。
2. **SFT 数据与提示格式。** `sft_example` 里把提示模板换成你的 chat 模板。提示权重为 0，回答权重为 1，其余不变。
3. **工程规模。** 示例用 `generate` 采样，生成器与训练模型在同一进程里。真实规模下，生成通常应交给专门的推理引擎，训练与生成各占一部分显卡，`--sync-every` 对应生成器同步权重的周期。示例没有实现分布式，损失分母要在所有卡上汇总后再除，否则每张卡各除各的会悄悄改变权重，这一点论文没有讨论，是实现上的推论，需要自己验证。
4. **微调方式。** 全参数或 LoRA 都可以接，示例没有内置 LoRA。用 LoRA 时 RL 的生成器要用合并后的权重或同一个带适配器的模型。

## 建议的做法与对照

按改动成本从低到高。

1. **检查点选择。** 保留 SFT 与 RL 各阶段的检查点，放到同一套下游任务上评测，包括未训练过的编辑类型、通用指令遵循和一份真正留出的 SFT 语料，按最终表现选。
2. **RL 期间混入 SFT 示范。** 对照组不混，实验组混入 0.5% 到 5% 的 SFT 数据（按损失 token 占比），其余完全相同。先用较小比例，论文测的范围是 0.5% 到 5%，示例里用 15% 只是为了在小模型上看出效应，不要照搬。
3. **MaxRL 与 REINFORCE 对照。** 论文里 MaxRL 的覆盖率更高，REINFORCE 的准确率与保留性更好，在 `rl_weights` 里一个开关切换。
4. **配比曲线。** 试半程退火、线性衰减。论文里混入的时机是独立的变量。

每一步的对照协议相同，同一个初始化、同一条数据流、同样的算力，多个种子，同时报准确率、覆盖率（pass@k）和保留性。
